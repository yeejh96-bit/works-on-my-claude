## 절대 규칙
- 아래에 적힌 파일/폴더만, 적힌 내용 그대로 생성한다. (매 프로젝트 항상 동일)
- 프로젝트마다 달라지는 것(기술 스택, 사용하는 MCP 등)은 채우지 않는다. 빈 틀만 둔다.
- `.mcp.json` 은 만들지 않는다.
- 코드 구현은 하지 않는다. 구조 생성까지만 한다. `CLAUDE.md` 「프로젝트 상세」의 세 칸은 **빈 틀로 둔다** — 코드를 훑어 대신 채우지 않는다(코드가 스펙이다).
- 생성하기 전에 먼저 `Glob` 로 현재 폴더에 같은 이름 파일이 이미 있는지 확인한다.
  이미 있는 파일은 **덮어쓰지 말고 건너뛰며**, 어떤 파일이 이미 있었는지 마지막 안내에서 알려준다.
- 단, **기존 프로젝트 온보딩**일 때는 이미 있는 `CLAUDE.md`·`.claude/settings.json` 을 그냥 건너뛰지 않고 womc 내용을 **덧붙여 병합한다** — 사용자가 쓴 내용은 한 줄도 지우지 않고 추가만 한다(아래 '기존 프로젝트 온보딩' 참고).

## 생성할 파일과 내용

### 1) `CLAUDE.md`
아래 내용을 그대로 쓴다.

```markdown
# 작업 규칙 (모든 프로젝트 공통 · 불변)
<!-- womc:skeleton-version=3.6.0 -->

이 파일은 매 세션 자동으로 로드된다. 아래 규칙은 프로젝트와 상관없이 항상 적용된다.

## 나에 대해
- 나는 코딩을 모른다. 전문 용어는 풀어서 설명한다.
- 모든 설명·보고는 한국어로 한다.

## 서브에이전트 보고 규약 (서브에이전트로 호출됐을 때만)
- 메인 대화면 이 절을 무시한다. 네가 서브에이전트일 때만 따른다.
- 파일·로그 원문을 통째로 붙여넣지 않는다. `파일경로:줄번호` 로 위치만 가리킨다.
- 확실하지 않으면 "확인 못 함"이라고 분명히 적는다.

## 적극 위임 (오케스트레이터 방식)
- 너(메인)는 지휘자다. 일이 나뉘면 서브에이전트에 맡기고 결론만 받아 조립한다. 독립인 갈래는 한 메시지에서 동시에 돌린다.
- **무엇을 나눌지·언제 위임할지는 네가 정한다** — 파일 몇 개 이상 같은 문턱값은 두지 않는다.
- **어느 서브에이전트에 맡길지는 각 에이전트의 설명을 보고 네가 고른다.** 맞는 것이 없으면 내장 `general-purpose` 에 역할·지시를 담은 프롬프트로 즉석 위임한다. 코드 검토는 사용자에게 `/code-review` 를 권한다.
- **`paths` 가 붙은 규칙(`.claude/rules/제약-<영역>.md`)은 서브에이전트에 전달되지 않는다** — 그 규칙이 걸리는 파일을 맡길 때는 네가 읽어 위임 프롬프트 본문에 그대로 붙여 넣는다.
- **같은 작업 항목에서 재위임은 최대 2회다.** 2회를 쓰고도 실패하면 멈추고 사용자에게 보고한다 — 유료 플랜 한도가 있어 무한히 다시 시도하지 않는다.
- 한 번에 한 기능만 진행한다.
- 한 기능이 끝나면 새 세션으로 시작하길 권하고, 대화가 무거워지면 `/compact` 를 제안한다.

## 프로젝트 스킬·규칙 (모델이 만들고 쓰고 지운다)
- 이 프로젝트에서만 통하는 것(도메인 지식·반복 절차)은 `.claude/skills/<이름>/SKILL.md` 로, 앞으로 계속 지킬 제약은 `.claude/rules/제약-<영역>.md` 로 남긴다.
- 같은 일을 두 번 이상 하게 되면 스킬로 남기자고 먼저 제안한다 — 사용자가 시키기를 기다리지 않는다.
- 메인이든 서브에이전트든, 프로젝트 스킬이 있으면 적극적으로 먼저 쓴다.
- 안 쓰는 프로젝트 스킬은 지우자고 제안한다.

## 세션을 이어서 하기
- `PLAN.md`·`TASKS.md` 는 **필요할 때만 읽는다** — 하던 일을 이어가거나 기능 작업을 시작할 때. 각 항목에 「손댈 파일」·「이어 쓸 것」·「끝난 것으로 보는 조건」·「확인 방법」이 있어, 그 항목만 읽고도 일을 시작할 수 있다.
- 끝난 항목·끝난 설계 경위가 가는 곳은 `docs/CHANGELOG.md` 다(옮기는 시점은 「절차 지키기」의 커밋 불릿). 앞으로도 지킬 제약은 `.claude/rules/제약-공통.md`(골격을 설계·수정할 때) 또는 `.claude/rules/제약-<영역>.md`(그 영역 파일을 손댈 때)에 적는다 — 둘 다 맨 위 `paths` 로 켜지는 자리가 정해진다. `TASKS.md`·`PLAN.md` 에 쌓지 않는다. **한 사실은 한 곳에만 적는다.**
- 버전을 올리는 작업이면 같은 작업에서 `docs/CHANGELOG.md` 를 반드시 함께 갱신한다 — 맨 위에 기록을 더하고, 맨 아래 「버전 한 줄 요약 (색인)」에 한 줄을 더한다.

## 절차 지키기 (벗어나면 되돌리기)
- 사용자가 "○○ 만들자 / ○○ 고쳐줘"라고 하면 `plan-feature` 스킬로 진행한다. 아주 사소한 것이 아니면 절차 없이 바로 고치지 않는다.
- **되돌릴 수 있는 일은 묻지 않는다 — 대신 손대기 전에 체크포인트 커밋(지금 상태를 되돌릴 수 있게 저장)을 남긴다.** `git add`·`git commit` 은 묻지 않고 한다. `push` 는 하지 않는다. **커밋할 때마다 `TASKS.md` 의 끝난 항목을 `docs/CHANGELOG.md` 로 옮겨 같은 커밋에 넣는다 — 「나중에 옮긴다」는 없다.**
- **커밋으로도 못 되돌리는 것만 하기 전에 사용자에게 한 줄로 묻는다**: `git push` / 배포·외부로 보내기 / 데이터베이스 내용 지우기 / `git reset --hard` / 파일·폴더 지우기 / 폴더 밖으로 옮기기. 물을 때는 무엇이 사라지는지 쉬운 말로 함께 알린다(사용자는 코딩을 모른다).
- 폴백: git 저장소가 아니거나 커밋이 실패하면 체크포인트가 없다 — 그때는 되돌리기 어려운 일 전부를 하기 전에 묻는다.
- 한 번 좋다고 한 것이 **다음번까지 이어지지 않는다** — 되돌리기 어려운 일은 그때그때 다시 묻는다. (`.claude/settings.json` 의 `ask` 가 이걸 설정으로도 붙잡는다.)

### 3) `.claude/settings.json` (하네스 — 권한 기본값 + 상태줄)
아래 내용을 그대로 쓴다.
(`.claude/` 아래에는 실제 동작 파일만 둔다 — 안내용 README 를 만들지 않는다.
`.claude/rules/` 폴더도 미리 만들지 않는다 — `make-rule` 스킬이 첫 규칙을 만들 때 생긴다.
서브에이전트·스킬은 **womc 플러그인이 직접 제공하므로 파일로 만들지 않는다.**)
- `deny` 로 비밀키 파일(`.env` 와 그 변형)을 **하위 폴더 것까지**(`**/.env`) Claude가 읽지 못하게 막는다. (.gitignore 의 비밀키 제외와 같은 정책)
  단, 비밀이 없는 견본 파일(`.env.example`)은 읽을 수 있어야 하므로 — Claude가 "어떤 설정값이 필요한지" 파악하는 데 쓴다 —
  `.env.*` 처럼 통째로 막지 않고 **비밀이 들어가는 이름만 골라서** 막는다. (deny 는 allow 보다 우선이라, 통째로 막으면 견본만 예외로 풀 방법이 없다.
  흔한 이름 기준이므로 특이한 이름의 비밀 파일까지 다 잡지는 못한다 — 진짜 중요한 비밀은 프로젝트 폴더 밖에 둔다.)
  또한 이 차단은 파일 읽기 도구(Read)에만 걸린다. 터미널 명령으로 읽는 것까지 다 막지는 못한다.
- `allow` 는 **빈 목록으로 둔다.** `git status`·`Get-ChildItem` 같은 읽기 전용 명령은 Claude Code 가
  **기본으로 프롬프트 없이 허용**하므로 적을 필요가 없다 — Bash 뿐 아니라 **PowerShell 도 마찬가지**다(Windows 실측, 2026-08-10).
  v2.1.1 까지는 PowerShell 4줄을 박아 두었으나 불필요한 것으로 확인돼 뺐다. 필요한 것이 생기면 그때 추가한다.
- `push`·`reset` 같이 되돌리기 어려운 명령은 **`allow` 에는** 넣지 않는다 — 그건 매번 확인받는 게 맞다. 대신 아래 `ask` 로 잡는다.
- `ask` 에는 **커밋으로 되돌릴 수 없는 것만** 넣는다(`git push`·`git reset --hard`·파일 지우기·폴더 밖으로 옮기기).
  커밋·브랜치 삭제는 넣지 않는다 — 커밋은 묻지 않고 남기는 체크포인트고, 브랜치는 지워도 커밋이 남아 되돌릴 수 있다.
  **배포·데이터베이스 삭제는 프로젝트마다 명령이 달라 패턴으로 못 잡는다 — `CLAUDE.md` 「절차 지키기」의 산문 규칙이 맡는다.**
  `ask` 는 `allow` 를 이기므로, 권한 창에서 「항상 허용」을 눌러도 **이 명령들은 다음번에 또 묻는다.**
  CLAUDE.md 「절차 지키기」의 "한 번 좋다고 한 것이 다음번까지 이어지지 않는다"를 문장이 아니라 **설정으로 보장하는 자리**다.
  되묻는 횟수가 느는 건 아니다 — 지금도 매번 묻는다. 다만 실수로 「항상 허용」을 눌러도 풀리지 않을 뿐이다.
  목록을 **좁게 두는 것이 중요하다** — `Bash(git:*)` 처럼 넓히면 `git status` 같은 안전한 명령까지 묻게 된다.
- `statusLine` 은 터미널 하단 상태줄로 `.claude/statusline.js` 를 실행한다(4번 참고). Node.js 가 없으면 상태줄만 안 보일 뿐 다른 기능엔 지장 없다.
  **경로는 `${CLAUDE_PROJECT_DIR}` 를 앞에 붙인 절대 경로로 적는다** — 상대 경로(`node .claude/statusline.js`)로 두면 실행 위치가 프로젝트 루트가 아닐 때(worktree·`--add-dir` 등) 파일을 못 찾아 종료코드 1 로 죽는다.
  이 변수는 Claude Code 가 채워 주며 bash·PowerShell 양쪽에서 동작한다(PowerShell 에서는 `${env:CLAUDE_PROJECT_DIR}` 로 자동 치환된다).
  **`refreshInterval` 은 상태줄이 사라진 채로 남지 않게 하는 안전장치다(초 단위).** Claude Code 는 상태줄 명령이 한 번이라도 실패하거나 아무것도 안 찍으면
  직전 값을 남기지 않고 상태줄을 **통째로 지우고**, 그다음 사건(새 답변·모델 변경·토큰 변화 등)이 올 때까지 다시 실행하지 않는다.
  그래서 한 번 삐끗하면 「대화하다 보니 상태줄이 없어졌다」가 된다. `refreshInterval` 이 있으면 몇 초 뒤 저절로 되살아난다.

```json
{
  "statusLine": {
    "type": "command",
    "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/statusline.js\"",
    "refreshInterval": 10
  },
  "permissions": {
    "allow": [],
    "ask": [
      "Bash(git push:*)",
      "Bash(git reset --hard:*)",
      "Bash(rm:*)",
      "Bash(mv:*)",
      "PowerShell(git push:*)",
      "PowerShell(git reset --hard:*)",
      "PowerShell(Remove-Item:*)",
      "PowerShell(Move-Item:*)"
    ],
    "deny": [
      "Read(**/.env)",
      "Read(**/.env.local)",
      "Read(**/.env.*.local)",
      "Read(**/.env.development)",
      "Read(**/.env.production)",
      "Read(**/.env.test)",
      "Read(**/.env.staging)"
    ]
  }
}
```

### 4) `.claude/statusline.js` (하네스 — 상태줄, Node 필요)
아래 내용을 그대로, 한 글자도 바꾸지 않고 쓴다. Node.js 내장 모듈만 쓰고 하드코딩된 경로가 없어 어떤 프로젝트에도 그대로 쓸 수 있다.
stdin 으로 들어오는 JSON 을 읽어 모델명·컨텍스트 토큰 사용량·5시간/주간 사용한도·현재 폴더명을 첫 줄에, 세션 ID 를 둘째 줄에 찍는다(여러 줄 상태줄은 Claude Code 가 지원한다).
Node.js 가 설치돼 있어야 동작한다 — 없으면 이 파일은 그냥 아무것도 안 찍고, 상태줄만 안 보일 뿐 다른 기능엔 지장 없다.
**이 스크립트는 어떤 경우에도 종료코드 0 으로 끝나고 최소 한 줄은 찍도록 짜여 있다** — 예외·깨진 입력·stdin 지연을 전부 삼키고 대체 문구(`…`)라도 출력한다.
Claude Code 가 「실패하거나 빈 출력이면 상태줄을 통째로 지우고 다음 사건까지 그대로 둔다」로 동작하기 때문이다(3번의 `refreshInterval` 설명 참고).
그러니 이 파일을 고칠 때 `emit()`·`try/catch`·`uncaughtException`·3초 guard 를 걷어내지 말 것 — 그게 상태줄이 사라지지 않게 붙잡는 부분이다.

```javascript
#!/usr/bin/env node
// Claude Code statusline (jq-free, Node-based)
// Format: 1줄째 <model> │ <used>k/<ctx>k │ S:<5h>% W:<week>% │ <folder> / 2줄째 <session-id>
//
// 이 스크립트의 첫 번째 약속: 무슨 일이 있어도 0으로 끝나고, 반드시 한 줄은 찍는다.
// Claude Code 는 상태줄 명령이 실패하거나(0이 아닌 종료) 아무것도 안 찍으면
// 직전 값을 남기지 않고 상태줄을 통째로 지운다. 게다가 다음 사건(새 답변·모델 변경 등)이
// 올 때까지 다시 실행하지 않으므로, 한 번 삐끗하면 상태줄이 한참 빈칸으로 남는다.
// 그래서 예외·빈 입력·stdin 지연을 전부 삼키고 대체 문구라도 출력한다.
// (settings.json 의 refreshInterval 이 두 번째 안전장치다 — 몇 초마다 스스로 되살아난다.)

const FALLBACK = "…";
let done = false;

function emit(line) {
  if (done) return;
  done = true;
  try {
    process.stdout.write(line && line.trim() ? line : FALLBACK);
  } catch (e) {
    /* 여기서 더 할 수 있는 일은 없다 */
  }
}

// 어떤 예외도 상태줄을 지우지 못하게 한다.
process.exitCode = 0;
process.on("uncaughtException", () => emit(FALLBACK));
process.on("unhandledRejection", () => emit(FALLBACK));

// stdin 이 끝나지 않아도 3초 뒤에는 무언가를 찍고 빠져나온다.
const guard = setTimeout(() => {
  emit(FALLBACK);
  try {
    process.stdin.pause();
    process.stdin.destroy();
  } catch (e) {}
}, 3000);

let raw = "";
process.stdin.setEncoding("utf8");
process.stdin.on("error", () => emit(FALLBACK));
process.stdin.on("data", (c) => (raw += c));
process.stdin.on("end", () => {
  clearTimeout(guard);

  // 입력이 깨져도 멈추지 않는다 — 빈 객체로 두고 아래에서 기본값으로 채운다.
  let d = {};
  try {
    d = JSON.parse(raw) || {};
  } catch (e) {
    d = {};
  }

  const model =
    (d.model && (d.model.display_name || d.model.id)) || "Unknown";

  // Current root folder name (basename of the working directory)
  const dir =
    (d.workspace && (d.workspace.current_dir || d.workspace.project_dir)) ||
    d.cwd ||
    "";
  const folder = dir
    ? dir.replace(/[\/]+$/, "").split(/[\/]/).pop()
    : "";

  // Session id (useful for `claude --resume <id>`)
  const sid = d.session_id || "";

  const cw = d.context_window || {};
  const usedK = Math.round((cw.total_input_tokens || 0) / 1000);
  const ctxK = Math.round((cw.context_window_size || 0) / 1000);

  const rl = d.rate_limits || {};
  const five =
    rl.five_hour && rl.five_hour.used_percentage != null
      ? Math.round(rl.five_hour.used_percentage)
      : null;
  const week =
    rl.seven_day && rl.seven_day.used_percentage != null
      ? Math.round(rl.seven_day.used_percentage)
      : null;

  // green < 50, yellow < 80, red >= 80
  const colorPct = (label, val) => {
    if (val === null) return `${label}:--`;
    const code = val < 50 ? 32 : val < 80 ? 33 : 31;
    return `\x1b[${code}m${label}:${val}%\x1b[0m`;
  };

  let line = `${model} │ ${usedK}k/${ctxK}k │ ${colorPct("S", five)} ${colorPct("W", week)}`;
  if (folder) line += ` │ \x1b[36m${folder}\x1b[0m`;
  // Session id on its own second row
  if (sid) line += `\n\x1b[90m${sid}\x1b[0m`;
  emit(line);
});
```

## 기존 프로젝트 온보딩 (해당할 때만)
파일 생성을 마친 뒤, **폴더에 기존 코드가 있거나 이미 사용자가 쓴 `CLAUDE.md`·`.claude/settings.json` 이 있으면** 아래 온보딩을 진행한다. (신규 빈 폴더면 이 절 전체를 건너뛴다.)
아래 각 단계는 **자기 조건이 맞을 때만** 켜진다 — 관례 캡처·구조 제안은 *기존 코드가 있을 때*, CLAUDE.md·설정 조율은 *그 파일이 이미 있을 때*(코드가 거의 없어도).
어떤 단계든 **기존 코드·파일 내용은 지우거나 덮어쓰지 않는다** — 추가·병합·제안만 한다.

- **기존 코드 판단**: `Glob` 로 매니페스트(`package.json`·`pyproject.toml`·`go.mod`·`Cargo.toml`·`pom.xml`·`Gemfile`·`composer.json` 등)나 소스 폴더(`src/` 등)·실제 코드 파일이 보이면 기존 프로젝트다. 방금 만든 골격 파일·`.git`·`node_modules` 는 신호에서 뺀다.

### 1) 기존 `CLAUDE.md`·설정 조율 (이미 있을 때만)
프로젝트에 이미 **비-womc `CLAUDE.md`** 가 있으면(첫 줄이 골격의 `# 작업 규칙 (모든 프로젝트 공통 · 불변)` 이 아니면) 건너뛰지 말고 조율한다:
- 기존 파일을 읽고 **`Edit` 으로 맨 끝에만** 아래처럼 표시된 구획을 덧붙인다(파일을 통째로 다시 쓰지 말 것 — 사용자 내용을 실수로 바꾸는 걸 막는다). 사용자 내용은 한 줄도 바꾸지 않는다. 이미 `womc:` 구획이 있으면 다시 넣지 않는다.
~~~markdown

<!-- womc:begin — 이 구획만 /womc update 가 관리. 위쪽 사용자 내용은 건드리지 않음 -->
<!-- womc:skeleton-version=3.6.0 -->
《여기》
<!-- womc:end -->
~~~
《여기》 자리에 넣을 것: 위 1) `CLAUDE.md` 골격의 **본문을 맨 위 H1 제목(`# 작업 규칙 …`) 한 줄만 빼고 글자 그대로** 넣는다.
`## 나에 대해` 부터 `## 프로젝트 상세` 까지 7개 절이 전부 들어간다 — 신규 프로젝트가 받는 규칙과 똑같이 맞추기 위해서다.
요약하거나 이 안내 문장을 그대로 붙여 넣지 않는다. 넣는 것은 골격 본문뿐이다.
- 기존 `.claude/settings.json` 이 있으면 통째로 덮지 말고 **갱신 모드와 같은 방식**(사용자 항목 보존 + 이 문서의 기본 allow/deny 만 추가)으로 병합한다.
  이미 `statusLine` 항목이 있으면 그대로 두고 건드리지 않는다 — 없을 때만 이 문서의 기본 `statusLine`(`.claude/statusline.js` 실행)을 추가한다.
- 사용자의 기존 CLAUDE.md 가 언어·수정 방식 등 같은 주제를 이미 정해 뒀으면, 겹치는 부분을 마지막 안내에서 한 줄로 짚어 주되 사용자 문장은 지우지 않는다.
- 무엇을 병합했는지 마지막 안내에서 한 줄로 알린다.

### 1-b) 기존 `AGENTS.md` 감지 (있을 때만)
`Glob` 로 **프로젝트 루트의 `AGENTS.md` 만** 본다. 하위 폴더의 `AGENTS.md` 는 무시한다 — 항상 로드되는 자리가 아니다. 루트에 없으면 이 소절 전체를 건너뛴다.
- 이 소절은 1) 과 달리 **「비-womc `CLAUDE.md` 일 때만」이라는 조건에 매이지 않는다** — 골격 그대로인 `CLAUDE.md` 든, 온보딩이 `womc:begin/end` 구획을 덧붙인 `CLAUDE.md` 든 똑같이 켜진다.
- **먼저 사용자에게 한 줄로 묻고, 좋다는 답을 받은 뒤에만 넣는다.** 물을 때 쉬운 말로 무엇이 달라지는지 함께 알리고, `AGENTS.md` 의 **줄 수를 세어 함께 알린다.**
  예: "다른 AI 도구용 규칙 파일(`AGENTS.md`, N줄)이 있어요. `CLAUDE.md` 에서 불러오게 연결할까요? 연결하면 매 세션 그 N줄도 함께 읽힙니다."
  묻는 이유는 **항상 로드되는 양이 늘어나는 자리라 자동으로 결정하지 않는다**는 것이다.
- 좋다고 하면 `Edit` 으로 `CLAUDE.md` 의 **`## 프로젝트 상세` 제목 줄 바로 다음 줄**에 `@AGENTS.md` 한 줄을 더한다. 파일을 통째로 다시 쓰지 않는다.
- 이미 `@AGENTS.md` 줄이 있으면 아무것도 하지 않는다 — 여러 번 돌려도 한 줄만 남는다.
- 연결했는지, 사용자가 거절해 넣지 않았는지를 마지막 안내에서 한 줄로 알린다.

### 2) 코드 관례를 규칙으로 캡처 (제안 후에만)
기존 코드에 일관된 관례(명명·폴더 역할·포매팅·테스트 방식 등)가 보이면, 앞으로 유지보수가 그걸 따르도록 `.claude/rules/` 로 캡처할지 **먼저 한 줄로 제안**한다. 좋다고 하면:
- 관례를 조사해 뽑는다(`파일경로:줄번호` 근거).
- 영역이 뚜렷하면 `paths` 로 스코프한 규칙 파일을 만든다(예: 스타일 관례 → 맨 위 `paths: ["**/*.css"]`). 애매하면 만들지 않는다.
- 확실한 관례만 옮긴다 — 추측으로 규칙을 만들지 않는다. (형식은 `make-rule` 스킬과 같다.)

### 3) 구조 정리는 제안만 → `plan-feature` 로 넘김
코드·폴더 구조가 어질러져 보여도 **`/womc` 는 코드를 옮기거나 고치지 않는다.** 마지막 안내에서 한 줄로 제안만 한다:
- 예: "구조를 정리하고 싶으면 '구조 정리해줘'라고 하세요 — `plan-feature` 가 단계별로, 되돌릴 수 있게(커밋) 진행합니다."
- 사용자가 원하면 그때 `plan-feature` 리팩터 경로로 넘어간다. `/womc` 는 감지·제안까지만 한다.

온보딩을 마치면 무엇을 했는지(병합·AGENTS 연결·캡처·구조 제안 중 실제로 한 것)를 한국어로 한 줄씩 알리고 "맞는지 검토하고 고쳐 주세요"로 맺는다.

## 생성이 끝나면
먼저, 골격 생성을 모두 마친 뒤 마무리 안내 맨 앞에 아래 WOMC 로고 아트를 코드블록(```)으로 감싸 이 모양 그대로 한 번 출력한다.
(일부 파일을 건너뛴 경우에도 아트는 동일하게 맨 앞에 한 번 넣는다.) 아트와 태그라인을 출력하고 한 줄 비운 뒤, 아래 한국어 안내로 이어간다.

```
 __        _____  __  __  ____
 \ \      / / _ \|  \/  |/ ___|
  \ \ /\ / / | | | |\/| | |
   \ V  V /| |_| | |  | | |___
    \_/\_/  \___/|_|  |_|\____|

           works on my claude
```

그다음 한국어로 짧게 다음 단계를 안내한다. 예시:

> ✅ 기본 골격을 만들었어요.
> 다음 순서로 진행하면 됩니다.
> 1) `CLAUDE.md` 맨 아래 「프로젝트 상세」의 세 칸(**뭘 푸는가 · 안 만들 것 · 어디서 돌아가나**)을 채우세요. 스택·구조·기능은 코드를 보면 알 수 있어 적지 않습니다.
> 2) 기능을 만들거나 고칠 땐 그냥 "○○ 만들자 / ○○ 고쳐줘"라고 하세요. `plan-feature` 스킬이 켜져
>    큰 작업이면 계획(PLAN.md)·진행상태(TASKS.md)를 **그때 자동으로** 만들어 한 번에 하나씩 구현하고, 작은 수정이면 바로 고친 뒤 동작을 같이 확인합니다.
>
> ※ 폴더에 옛 `SPEC.md` 가 남아 있으면 — 새로 만든 골격은 이 파일을 읽지 않아요. 다만 원래 있던 `CLAUDE.md` 안에 `@SPEC.md` 줄이 남아 있으면 그 줄 때문에 아직 매 세션 읽힙니다. 정리하려면 "SPEC.md 정리해줘"라고 하세요 — 코드를 봐도 알 수 없는 내용만 「프로젝트 상세」 세 칸으로 옮기고 파일과 그 줄을 지워 드립니다.
> ※ PLAN.md·TASKS.md 는 지금 만들지 않습니다. 필요한 순간에만 생겨 평소 컨텍스트를 가볍게 둡니다.
> ※ 기존 프로젝트에 깐 경우, 구조가 어질러져 보이면 "구조 정리해줘"라고 하세요 — `plan-feature` 가 단계별로, 되돌릴 수 있게(커밋) 정리합니다.
> ※ MCP가 필요한 프로젝트라면 그때 `.mcp.json` 을 직접 추가하세요.
> ※ 터미널 하단 상태줄(모델명·토큰·5시간/주간 한도·폴더명 + 둘째 줄 세션 ID 표시)은 Node.js 가 설치돼 있어야 보여요. 없어도 다른 기능엔 지장 없습니다.
> ※ `.claude/` 폴더는 Claude Code 가 보호하는 자리라, 여기에 파일을 쓸 때는 권한 모드와 상관없이 **매번 물어봅니다** — 허용을 누르시면 됩니다.

안내를 내보내기 전에 **이 폴더가 git 저장소인지 확인한다**(`git rev-parse --git-dir`). 저장소가 아니면 위 안내 끝에 한 줄 덧붙인다:
"※ 아직 git 저장소가 아니에요. `git init` 을 해 두면 기능이 하나 끝날 때마다 되돌릴 지점(커밋)을 남길 수 있어요 — 해 드릴까요?"
(묻기만 한다. 사용자가 좋다고 할 때만 `git init` 을 실행한다. 저장소가 없으면 `plan-feature` 의 커밋 권유가 전부 실패하므로 이 확인을 건너뛰지 않는다.)

(코드를 짜지 말 것. 「프로젝트 상세」 세 칸도 대신 채우지 않는다 — 단, 기존 프로젝트면 위의 '기존 프로젝트 온보딩'까지는 한다. 코드 구조를 직접 옮기지도 않는다 — 필요하면 제안만 하고 멈춘다.)

## 갱신 모드 (`/womc update`)
인자에 `update` 가 있을 때만 이 절차를 수행한다. 원칙: **사용자가 채운 내용은 절대 건드리지 않고, 불변 골격만 이 문서의 최신 내용으로 교체한다.**

**이 절의 「옛 것 지우기」 항목에는 끝나는 조건이 있다 — 목록은 늘어나기만 하지 않는다.** 어떤 항목이 들어온 뒤 골격 버전으로 **두 판 이상 지나도록 실제로 그 항목에 걸린 프로젝트를 한 번도 못 봤으면 그 항목을 목록에서 뺀다**(그만큼 옛 설치본이 안 남아 있다는 뜻이다). 뺄 때는 `docs/CHANGELOG.md` 에 무엇을 언제 왜 뺐는지 한 줄 남긴다 — 나중에 그 옛 설치본이 나타나면 되살릴 근거가 된다.
**걸린 프로젝트를 한 번이라도 봤으면 그 판부터 다시 센다.**

0. **먼저 플러그인 자체를 최신으로 올린다.** (`/womc update` 한 번으로 플러그인 갱신까지 끝나게 하기 위해서다.)
   - Bash 로 실행한다: `claude plugin update womc@works-on-my-claude`
   - 성공하면 설치 캐시가 최신 버전으로 바뀐다. 다만 **지금 이 세션은 이미 읽어 둔 옛 명령 파일을 계속 쓴다** — 그래서 이번 실행분은 아래 0-b 에서 최신 문서를 직접 받아 적용한다. 캐시 갱신 효과는 다음 세션부터 나타난다.
   - 실패해도(CLI 없음·네트워크 차단·권한 거부) 멈추지 않는다. 한 줄만 알리고 0-b 로 넘어간다.
   - 무엇이 어떻게 됐는지(이미 최신이었는지 / 어느 버전으로 올랐는지 / 실패했는지)는 마지막 완료 보고에 한 줄로 적는다.
   - 참고: 이 지시는 1.15.0 부터 들어갔다. 그보다 옛 캐시로 도는 세션은 이 단계를 읽지 못하므로 플러그인이 자동으로 갱신되지 않는다 — 그때는 0-b 가 GitHub 최신 골격을 받아 적용하고, 사용자에게 `/plugin` 수동 업데이트를 안내한다.

0-b. **최신 골격 문서를 직접 받아 온다. 지금 실행 중인 이 문서가 옛 캐시일 수 있기 때문이다.**
   - 받을 곳(womc 공식 저장소 — 이 URL 을 다른 것으로 바꾸지 않는다):
     `https://raw.githubusercontent.com/yeejh96-bit/works-on-my-claude/main/commands/womc.md`
   - 받는 방법: 임시 파일로 저장한 뒤 Read 로 읽는다. (WebFetch 는 내용을 요약·변형할 수 있어 골격 원문에는 쓰지 않는다.)
     `curl -fsSL <URL> -o "${TMPDIR:-${TEMP:-/tmp}}/womc-latest.md"` — Bash 도구는 Windows 에서도 Git Bash(POSIX sh)라 이 한 줄이 모든 OS 에서 통한다.
     (`%TEMP%\...` 같은 cmd.exe 표기는 Git Bash 에서 확장되지 않아 프로젝트 폴더에 `%TEMP%\womc-latest.md` 라는 이름의 파일이 생긴다 — 쓰지 않는다.)
   - 받은 문서 맨 위의 `womc:skeleton-version=` 값이 "최신 버전", 지금 실행 중인 이 문서의 값이 "실행 중 버전"이다.
     (실행 중 문서에 표식이 아예 없으면 1.12.0 이하의 옛 캐시다.)
   - **최신 버전 > 실행 중 버전이면, 지금 이 문서의 내용은 버리고 받아 온 문서의 갱신 모드 절차와 파일 템플릿을 따른다.**
     사용자에게 한 줄 알린다. 예: "옛 캐시(1.10.0)로 실행 중이라 GitHub 에서 최신 1.14.0 골격을 받아 적용한다."
     **받아 온 문서의 0·0-b 단계는 다시 수행하지 않는다**(이미 최신을 손에 쥐었다 — 또 받으면 끝없이 반복된다). 그 문서의 1번부터 따른다.
   - 같으면 그대로 이 문서로 진행한다.
   - **다운그레이드 방지**: 프로젝트의 `CLAUDE.md` 맨 위에 `womc:skeleton-version=` 이 찍혀 있으면 그 값이 "지금 깔린 골격 버전"이다.
     적용하려는 버전이 그보다 **낮으면 아무것도 고치지 말고 멈춘 뒤** 사용자에게 알린다. 예: "지금 깔린 골격은 1.19.0 인데 적용하려는 건 1.14.0 이다. 옛 버전으로 되돌리면 손해라 멈췄다. 그래도 되돌리려면 다시 말해 달라." (표식이 없으면 1.18.0 이하이므로 그냥 진행한다.)
   - 받기에 실패하면(인터넷 차단·curl 없음) 순서대로 물러선다:
     ⓐ 로컬 마켓플레이스 클론에서 읽어 본다 — Windows `C:\Users\<사용자>\.claude\plugins\marketplaces\works-on-my-claude\commands\womc.md`, mac·linux `~/.claude/plugins/marketplaces/works-on-my-claude/commands/womc.md`
     ⓑ 그것도 안 되면, 실행 중 버전이 옛 캐시로 의심될 때(표식 없음)만 **아무것도 고치지 말고 멈춘 뒤** 이렇게 안내한다: `/plugin` 에서 works-on-my-claude → womc 업데이트 → **Claude Code 를 껐다 켠 뒤** → `/womc update` 재실행. (세션 도중 업데이트해도 그 세션은 옛 명령 파일을 계속 쓴다.)
     ⓒ 표식이 있고 최신 확인만 실패한 경우에는 "최신 여부를 확인하지 못했다"고 한 줄 알린 뒤 이 문서로 진행한다.
   - 임시 파일은 다 쓰고 지운다.
   - **0단계의 플러그인 갱신이 실패했을 때만**, 최신을 받아 썼다면 완료 보고에 이렇게 덧붙인다: 플러그인 자체는 아직 옛 버전이니 편할 때 `/plugin` 에서 한 번 업데이트해 두면 다음부터는 받아 오지 않아도 된다. (0단계가 이미 성공했다면 이 안내는 하지 않는다.)
   - 참고: 설치된 캐시 버전은 `~/.claude/plugins/installed_plugins.json` 의 `womc@works-on-my-claude` 항목(`version`·`lastUpdated`)에서도 볼 수 있다 — 사용자가 "업데이트했는데 왜 옛날 거냐"고 하면 이걸 보여주며 설명한다.

1. 아래 불변 골격 파일들을 이 문서에 적힌 내용 그대로 **덮어쓴다**(없으면 새로 만든다).

   > **덮기 전 공통 확인 — 골격이 맞는지 먼저 본다.** 아래 각 파일을 덮기 전에 기존 파일을 **먼저 읽어**, 그게 womc 가 만든 것인지 사용자가 만든 것인지 가른다.
   > 판정: 파일 첫 줄(또는 `.md` 의 frontmatter `name:`)이 이 문서의 골격 원문과 같으면 womc 것 → 덮는다.
   > **다르면 사용자 파일이다 → 덮지 말고 건너뛰고**, 완료 보고에 "○○ 는 당신이 쓴 파일로 보여 그대로 뒀다. 골격 것으로 바꾸려면 그 파일을 지우고 `/womc update` 를 다시 실행하면 된다"고 알린다.
   > (`explore`·`plan` 같은 이름은 흔해서 사용자가 이미 같은 이름으로 만들어 뒀을 수 있다. 생성 모드는 이런 파일을 건너뛰므로, 갱신 모드만 지우면 앞뒤가 안 맞고 복구도 불가능하다.)

   - `CLAUDE.md` — 세 경우로 나뉜다: ⓐ 첫 줄이 골격 그대로(`# 작업 규칙 (모든 프로젝트 공통 · 불변)`)면 **통째로 덮지 말고 절 단위로 병합한다**(바로 아래 절차). ⓑ **온보딩으로 사용자 파일에 병합된 형태(`womc:begin` 이 들어간 줄부터 `womc:end` 가 들어간 줄까지의 구획이 있는 경우)면 그 구획 안만 최신 내용으로 교체**하고 나머지 사용자 내용은 그대로 둔다. ⓒ 둘 다 아니면(사용자가 쓴 CLAUDE.md 인데 온보딩 병합을 안 거친 경우) **통째로 덮지 말고**, 위 '기존 프로젝트 온보딩'의 CLAUDE.md 병합 절차대로 `womc:begin/end` 구획을 맨 끝에 덧붙인다(사용자 내용 보존).
     ⓑ 의 구획을 찾을 때는 `<!-- womc:begin -->` 처럼 **정확히 일치하는 문자열을 찾지 않는다** — 실제 표식에는 뒤에 설명 문구가 붙어 있다. `womc:begin` 이라는 문자열이 **들어 있는 줄**을 시작으로, `womc:end` 가 들어 있는 줄을 끝으로 잡는다. (정확 일치로 찾으면 못 찾아 ⓒ 로 빠지고, 그러면 `/womc update` 를 돌릴 때마다 골격 한 벌이 계속 덧붙어 매 세션 로드량이 배로 늘어난다.)
     ⓑ 로 구획 안을 교체할 때는 **구획을 갈아끼우기 전에 `## 프로젝트 상세` 절을 통째로 떼어 뒀다가, 교체한 뒤 같은 자리에 되돌린다** — 이 절의 본문은 사용자가 쓴 것이라 골격 원문으로 덮으면 안 된다(판정은 아래 ⓐ 2-b 특례를 그대로 쓴다). **import 줄(`@AGENTS.md`·`@SPEC.md`)은 그 절 안에 있어 둘 다 함께 이월된다** — 온보딩에서 사용자가 이미 승낙했거나 사용자가 직접 쓴 줄이므로 **다시 묻지 않고, 한 줄도 지우지 않는다.** 2-b 판정이 「옛 골격 원문」이면 그때만 3소절 템플릿으로 바꿔 되돌리고, 그 import 줄들은 `## 프로젝트 상세` **제목 줄 바로 다음 줄**에 넣는다.
     **ⓐ 의 절 단위 병합 절차.** 첫 줄이 골격 그대로여도 **파일 중간에 사용자가 직접 써 넣은 절이 있을 수 있다** — 실측 사례: 골격의 「절차 지키기」 절과 「프로젝트 상세」 절 사이에 그 프로젝트만의 절대 원칙 절(개인정보를 LLM 에 보내지 말 것 등)이 들어 있었다. 통째로 덮으면 그게 전부 사라진다. 그래서 이렇게 한다:
     1. 기존 파일을 읽어 `## ` 로 시작하는 제목을 경계로 절을 쪼갠다.
     2. **아래 「골격 절 제목 7개」에 해당하는 절만** 이 문서 1번 절의 `CLAUDE.md` 템플릿 내용으로 교체한다(순서도 템플릿과 같다):
        `## 나에 대해` · `## 서브에이전트 보고 규약 (서브에이전트로 호출됐을 때만)` · `## 적극 위임 (오케스트레이터 방식)` · `## 프로젝트 스킬·규칙 (모델이 만들고 쓰고 지운다)` · `## 세션을 이어서 하기` · `## 절차 지키기 (벗어나면 되돌리기)` · `## 프로젝트 상세`
        **템플릿의 절 제목을 바꾸면 이 목록도 같은 작업에서 함께 고친다** — 안 고치면 그 절이 「사용자가 쓴 절」로 오인돼 옛 판이 영원히 남는다.
     2-b. **`## 프로젝트 상세` 는 특례 — 제목만 골격 것이고 본문은 사용자 것이다.** 위 2단계 목록에 들어 있지만, 이 절만은 본문을 골격 원문으로 덮지 않는다(v3.1.0. 덮으면 사용자가 적어 둔 「뭘 푸는가·안 만들 것·어디서 돌아가나」가 통째로 날아간다).
        판정은 **글자 대조가 아니라 구조로** 한다 — 본문이 프로젝트마다 달라 골격 원문과의 글자 대조가 성립하지 않는다:
        - 절 본문이 `@SPEC.md`(또는 `@AGENTS.md`) import 줄과 안내 한 줄 정도뿐이고 **사용자가 쓴 내용이 없으면** 옛 골격 원문으로 본다 → 절 본문을 새 골격의 3소절 템플릿(위 1번 `CLAUDE.md` 템플릿의 「프로젝트 상세」 세 소절, 내용은 빈 틀)으로 교체한다.
          **있던 import 줄(`@AGENTS.md`·`@SPEC.md`)은 둘 다 한 줄도 지우지 않고** 아래 7단계대로 `## 프로젝트 상세` 제목 바로 다음 줄로 되돌린다.
        - **사용자가 쓴 내용이 한 줄이라도 있으면** 절을 통째로 그대로 둔다 — 제목 줄만 골격 것으로 맞추고 본문은 한 줄도 손대지 않는다.
        - 그대로 뒀는데 세 소절이 없으면 여기서 억지로 끼워 넣지 않는다 — 아래 6번 완료 보고에서 세 칸을 채워 달라고 안내만 한다.
     3. **없어진 골격 절 지우기 — 아래 4단계(사용자 절 판정)보다 먼저 한다.** 아래 제목의 절은 옛 womc 골격이 만든 것이다. 지금 골격에는 없으니 **사용자 절로 보지 말고** 이렇게 처리한다: `## 코드 제공 방식` · `## 설명 방식`
        - 절 본문이 옛 골격 원문(역대 판본 포함)으로 보이면 **절째 지운다.**
        - 사용자가 문장을 더한 흔적이 있으면 지우지 말고 두되, 완료 보고에 "이 절은 이제 골격에 없다 — 필요 없으면 지워도 된다"고 알린다.
        - 지웠는지 남겼는지를 **절 이름과 함께** 완료 보고에 적는다.
        - **앞으로 골격에서 절을 뺄 때마다 이 목록에 그 제목을 더한다** — 안 더하면 옛 절이 사용자 절로 오인돼 영영 남는다. (반대로 오래된 항목은 이 절 맨 앞의 「끝나는 조건」에 따라 뺀다.)
        - v3.1.0 에서 더할 절은 없다 — 그 판이 뺀 것은 `SPEC.md` **파일**이지 절이 아니다. `## 프로젝트 상세` 절은 그대로 남으며 위 2-b 특례로 다룬다.
     4. **위 2·3 어느 목록에도 없는 제목의 절은 사용자가 쓴 것이다 — 원래 순서 자리에 그대로 남긴다.** (바로 앞에 있던 골격 절 뒤에 붙여 두면 원래 자리가 유지된다.)
     5. 골격에는 있는데 기존 파일에 없는 절은 골격 순서대로 새로 넣는다.
     6. 맨 위 H1 제목 줄과 `womc:skeleton-version` 표식 줄은 최신 골격 것으로 맞춘다.
     7. **덮기 전에 있던 import 줄(`@AGENTS.md`·`@SPEC.md`)은 둘 다 이월한다 — 한 줄도 지우지 않는다.** 기존 파일의 `## 프로젝트 상세` 절에 그 줄이 있었으면, 교체한 뒤에도 **`## 프로젝트 상세` 제목 줄 바로 다음 줄**에 다시 넣는다(온보딩 '기존 `AGENTS.md` 감지'와 같은 자리다). 사용자가 이미 승낙했거나 직접 쓴 표시이므로 **다시 묻지 않는다.** (이월하지 않으면 `/womc update` 한 번에 그 연결이 조용히 사라지고 사용자는 알아챌 방법이 없다 — 연결을 끊는 건 사용자만 할 수 있다.)
        이 절은 위 2-b 특례라 통째로 교체되지 않으므로, **2-b 에서 실제로 교체가 일어난 경우에만** 이월이 필요하다(본문을 그대로 둔 경우엔 그 줄이 이미 절 안에 남아 있다).
     ⓐ 로 병합했으면 **그대로 남긴 사용자 절의 제목 목록**을 완료 보고에 한 줄 적는다.
     **루트에 `AGENTS.md` 는 있는데 `CLAUDE.md` 에 `@AGENTS.md` 줄이 없으면 자동으로 넣지 않는다(ⓐ·ⓑ 모두 해당).** 완료 보고(6번)에 한 줄 제안만 한다. 쉬운 말 예: "`AGENTS.md` 가 있는데 `CLAUDE.md` 에 연결돼 있지 않아요. 연결하면 매 세션 그 내용도 함께 읽힙니다 — 연결할까요?" 갱신이 말없이 넣지 않는 이유는 **이미 깔린 프로젝트를 조용히 무겁게 만들지 않기 위해서다** — 연결하는 만큼 매 세션 항상 로드되는 양이 늘어나므로 사용자가 골라야 한다.
     **import 줄(`@AGENTS.md`·`@SPEC.md`) 처리 결과를 완료 보고에 한 줄 적는다.** 이때 **「루트에 그 파일이 있는지」와 「`CLAUDE.md` 안에 그 import 줄이 있는지」는 별개이므로 두 축을 나눠 판정한다** — 줄을 이월했는지 / (`AGENTS.md` 는) 연결을 제안만 했는지 / 파일도 줄도 없어 해당 없음이었는지.
     **깨진 연결 — 루트에 `SPEC.md` 는 없는데 `CLAUDE.md` 에 `@SPEC.md` 줄만 남아 있으면** 그 줄은 이월하되(지우지 않는다) 완료 보고에 그 사실을 쉬운 말로 한 줄 알린다. 예: "`CLAUDE.md` 에 `@SPEC.md` 줄이 있는데 그 파일이 없어요. 이 줄은 아무것도 불러오지 않습니다(오류는 안 뜨고 조용히 무시돼요) — 지울까요?" **묻기만 하고 스스로 지우지는 않는다**(위 4번 「절대 건드리지 않는 것」 그대로다). `@AGENTS.md` 가 같은 상태여도 같은 방식으로 알리기만 한다.
   - `.claude/statusline.js` — 코드 자체는 항상 최신으로 덮어쓴다(사용자가 직접 고칠 일이 없는 스크립트라서). 단, `settings.json` 의 `statusLine` 키를 켜고 끄는 건 아래 3번을 따른다.

   - 판정은 **위 1번의 「덮기 전 공통 확인」을 그대로 쓴다** — 각 파일을 먼저 읽어 womc 원본인지 사용자가 고친 것인지 가른다.

     **git 저장소가 아니거나 커밋이 실패하면 지우기 전에 사용자에게 한 줄로 묻는다**(무엇이 사라지는지 쉬운 말로 함께 알린다). 좋다는 답을 받은 것만 지운다.
   - **womc 원본이면 지운다.** 지운 것을 완료 보고에 **한 줄씩** 적고, "이제 womc 플러그인이 직접 제공하거나 골격에서 빠져서 지웠다. 체크포인트 커밋이 있어 되돌릴 수 있다"고 알린다.

   - `.claude/agents/`·`.claude/skills/`·`.claude/output-styles/` 폴더가 비게 되면 폴더도 지운다. 사용자 파일이 남아 있으면 폴더는 그대로 둔다.

3. `.claude/settings.json` 은 통째로 덮어쓰지 않는다. 기존 파일을 먼저 읽고,
   **사용자가 직접 추가한 항목(allow/deny 등 이 문서의 기본값에 없는 것)은 그대로 둔 채** 기본값 항목만 최신으로 맞춰 다시 쓴다.
   (기존 파일이 없으면 기본값으로 새로 만든다. 예전 기본값이던 `Read(**/.env.*)` 가 있으면 위의 새 deny 목록으로 교체한다 — 견본 `.env.example` 을 읽을 수 있게 하기 위해서다.)
   **`allow` 에 옛 골격의 PowerShell 4줄(`PowerShell(git status:*)`·`(git diff:*)`·`(git log:*)`·`(Get-ChildItem:*)`)이 있으면 그 4개만 지운다** — v2.2.0 에서 뺀 옛 기본값이다. 읽기 전용 명령은 Bash·PowerShell 모두 Claude Code 가 기본으로 프롬프트 없이 허용하므로 필요 없다(Windows 실측, 2026-08-10). **그 4개 말고 `allow` 에 들어 있는 항목은 사용자가 직접 넣은 것이므로 한 줄도 건드리지 않는다.**
   **옛 4줄을 실제로 지웠는지, 아니면 애초에 없어서 지울 게 없었는지를 완료 보고(6번)에 반드시 한 줄 적는다** — 이 청소는 한 번뿐이라 지금이 실제로 지워졌는지 확인할 유일한 기회이고, 아래 7번이 그 결과를 열린 확인 `open:allow-cleanup` 을 닫는 근거로 쓴다.
   **`ask` 키가 없으면 이 문서의 기본 `ask` 목록을 통째로 추가한다.** 되돌리기 어려운 명령을 「항상 허용」으로 풀어버리지 못하게 막는 자리다(위 「3) `.claude/settings.json`」 참고).
   **이미 `ask` 가 있으면 사용자가 넣은 항목은 한 줄도 지우지 않고, 이 문서의 기본 항목 중 빠진 것만 더한다.**
   `statusLine` 은 다르게 다룬다 — 이미 있으면(사용자가 커스텀했을 수 있으므로) **값을 덮어쓰지 않고 그대로 둔다**. 아예 없을 때만 이 문서의 기본 `statusLine`(`.claude/statusline.js` 실행)을 새로 추가한다.
   **딱 하나 예외**: 기존 `command` 가 옛 womc 기본값 `node .claude/statusline.js` **글자 그대로**이면(= 사용자가 손댄 적이 없다는 뜻) 이 문서의 새 기본값으로 **교체한다** —
   상대 경로 + `refreshInterval` 없음 조합이 v2.10.1 에서 고친 「상태줄이 대화 도중 사라져 돌아오지 않는」 버그의 원인이라, 그대로 두면 고침이 옛 프로젝트에 닿지 않는다.
   글자가 조금이라도 다르면 사용자가 고친 것으로 보고 건드리지 않는다. 교체했으면 마지막 보고에 한 줄로 알린다.
   **`ask` 에 옛 골격의 브랜치 삭제 4줄(`Bash(git branch -d:*)`·`Bash(git branch -D:*)`·`PowerShell(git branch -d:*)`·`PowerShell(git branch -D:*)`)이 있으면 그 4개만 지운다** — v2.x 옛 기본값이다. 브랜치를 지워도 커밋이 남아 되돌릴 수 있어 v3.0.0 에서 뺐다. **그 4개 말고 `ask` 에 들어 있는 항목은 사용자가 넣은 것이므로 한 줄도 건드리지 않는다.** 지웠는지, 애초에 없었는지를 완료 보고에 한 줄 적는다.

   **그 밖의 값이 들어 있으면 사용자가 고른 것이므로 지우지 않고 그대로 둔다** — 그대로 뒀다고 완료 보고에 한 줄만 알린다.
   `hooks` 는 이렇게 다룬다 — 위 2번에서 `answer-style.js` 를 지웠으면 `node .claude/answer-style.js` 를 실행하는 `UserPromptSubmit` 항목도 함께 뺀다(스크립트가 없는데 훅만 남으면 매 입력마다 실패한다). 그 결과 `hooks` 가 비면 키째 지운다. 사용자가 직접 넣은 다른 훅은 건드리지 않는다.

7. **하네스 감사 (자동).** 위 1~6번으로 골격 갱신을 마쳤으면 곧바로 이어서 한다 — 사용자가 따로 부르지 않아도 된다.
   - `docs/HARNESS-AUDIT.md` 의 맨 위 기록에 적힌 「마지막 감사 기준 버전」을 지금 `claude --version` 과 비교한다. 파일이 없으면 이번이 첫 감사다 — 그냥 진행한다.
     **버전 비교는 앞 두 자리(`major.minor`)로만 한다.** 예: 기준 `2.1.226` vs 현재 `2.1.228` 이면 **같은 것으로 본다**(패치만 오름). `2.2.0` 이나 `3.0.0` 이면 다른 것이다. 세 번째 자리(패치)는 대개 버그 수정이라 골격을 바꿀 만한 신기능이 없어서다.
   - **감사 본체를 도는 조건은 하나다 — Claude Code 앞 두 자리가 지난 감사와 다르다.**
   - **앞 두 자리가 같으면 감사 본체를 건너뛴다** — 한 줄로 알리되 두 경우를 구분한다: 버전이 완전히 같으면 "지난 감사 이후 Claude Code 가 안 바뀌었음", 패치만 다르면 "패치만 올랐음(2.1.226 → 2.1.228) — 버그 수정 위주라 신기능 조사는 건너뜀". 이어서 **"그래도 지금 조사할까요?" 한 줄을 덧붙인다** — 사용자가 좋다고 하면 아래 「다르면」과 똑같이 `harness-audit` 스킬을 그 자리에서 실행한다.
     **건너뛰더라도 `docs/HARNESS-AUDIT.md` 머리의 `womc:open-checks` 구획(`womc:open-checks:begin` 이 들어 있는 줄부터 `womc:open-checks:end` 가 들어 있는 줄까지)은 반드시 읽어, 열린 확인 항목이 있으면 한 줄씩 사용자에게 알린다.** 그 항목의 전문(조건·확인 방법)은 `TASKS.md` 「할 일」에 있으니 필요하면 거기서 읽어 온다.
     위 3번에서 옛 `allow` 4줄을 **실제로 지웠다면 그 사실이 열린 확인 `open:allow-cleanup` 의 확인 결과**이므로 함께 알리고, `TASKS.md` 의 그 항목을 닫아도 되는지 사용자에게 묻는다. (`TASKS.md` 를 말없이 고치지 않는다 — 사용자가 좋다고 할 때만 닫는다.)
   - **어느 가지로 가든, 먼저 `docs/HARNESS-AUDIT.md` 머리의 `womc:open-checks` 구획을 읽어 열린 확인이 있으면 한 줄씩 알린다.** 건너뛸 때만 알리면, 감사가 도는 사이클에서는 목록이 화면에서 사라진다.
   - **버전 앞 두 자리가 다르면** `harness-audit` 스킬을 그 자리에서 실행한다. 이때 조사 구간은 패치까지 포함한 **「마지막 감사 기준 버전 ~ 현재 버전」 전체**다. (스킬 절차를 여기 베껴 적지 않는다 — 절차의 진실은 `skills/harness-audit/SKILL.md` 한 곳에만 둔다.)
   - 스킬이 「뺄 수 있음」이나 **「새로 들일 것」**을 하나라도 찾으면 **파일을 바로 고치지 말고 사용자에게 한 번 묻는다.** 쉬운 말 예: "지금 골격에서 빼도 되는 게 N개, 새로 들일 만한 게 M개 나왔음. 지금 반영할까요, 기록만 남길까요?" 사용자가 좋다고 하면 `plan-feature` 로 넘어가 반영한다. **뺄 것과 들일 것은 나눠 묻는다** — 한쪽만 고를 수 있어야 한다.
     **묻지 않고 지우거나 새로 넣는 일은 없다** — 골격을 손대는 건 되돌리기 번거롭고, 근거가 틀리면 잘 돌던 세팅이 깨지기 때문이다.
   - `harness-audit` 스킬이 없거나(플러그인 캐시가 옛 판) 실행이 안 되면 **조용히 건너뛰고** 갱신 자체는 성공으로 끝낸다 — 감사 때문에 갱신이 실패해서는 안 된다.
8. **쌓인 것 훑기 (갱신이 끝난 뒤 한 번).** 위 7번까지 마쳤으면 이어서 한다. 갱신은 골격을 최신으로 갈아 줄 뿐이라 **그 프로젝트에 이미 쌓여 있는 것은 아무도 보지 않는다** — 갱신이 끝나는 이 자리에서 한 번 훑는다.
   - **여섯 가지를 본다. 각각 결과를 쉬운 말로 한 줄씩 알린다**(사용자는 코딩을 모른다 — 무엇이 왜 문제인지 한 줄에 같이 담는다). 어떻게 찾을지는 정해 두지 않는다.
     ① `TASKS.md` 에 끝난 항목(`[x]`)이 남아 있는지, 남아 있으면 그 파일이 몇 줄인지. (v3.3.0 부터 `TASKS.md` 에는 끝남 표기가 없다 — `[x]` 가 보이면 옛 방식으로 쌓인 것이다.)
     ② `.claude/rules/` 에서 맨 위에 `paths` 가 없는 규칙 파일(= 매 세션 항상 읽히는 것)이 몇 줄인지.
     ③ `CLAUDE.md` 에 **같은 제목의 절이 두 벌** 있는지 — 갱신이 여러 번 돌면서 겹쳤을 수 있다.
     ④ `SPEC.md` 같은 명세·요약 문서가 `CLAUDE.md` 의 `@파일명` 줄로 연결돼 **매 세션 읽히고 있는지.**
     ⑤ `.claude/skills/` 는 비어 있는데 `.claude/rules/` 안에 「이럴 땐 이런 순서로」 같은 **반복 절차가 규칙으로 섞여** 있는지 — 절차는 스킬 자리다.
     ⑥ `.claude/rules/` 의 규칙이 **지금 이 프로젝트의 실제 설정·파일과 어긋나는지** — ⓐ 「안 한다」고 적힌 것을 설정이나 공식 파일이 실제로는 쓰고 있는지, ⓑ 「전문은 저기 있다」는 포인터가 가리키는 파일·절이 실제로 있는지, ⓒ 확인할 방법도 계기도 없이 열린 채 남은 항목이 있는지.
     쉬운 말 예: "할 일 목록에 끝난 항목이 남아 파일이 278줄입니다 — 끝난 것은 기록 파일로 보내면 됩니다."
     ⑥ 의 쉬운 말 예: "규칙에 '○○는 안 한다'고 적혀 있는데 설정에는 ○○가 켜져 있습니다."
     **여섯 가지 다 걸린 게 없으면 "쌓인 것 없음" 한 줄로 끝낸다.**
     **몇 줄이 넘으면 정리해야 한다는 기준선은 두지 않는다** — 몇 줄인지 세어서 알리기만 하고, 정리할지는 사용자와 함께 정한다.
   - **이 폴더가 git 저장소면 묻지 않고 정리에 들어간다** — 체크포인트 커밋이 있어 되돌릴 수 있기 때문이다(위 2번의 지우기와 같은 이유다). 정리가 끝나면 무엇을 했는지 한 줄로 알린다.
   - **git 저장소가 아니면 정리 전에 한 번 묻는다** — 되돌릴 자리가 없기 때문이다. 물을 때 무엇이 어디로 옮겨지는지 쉬운 말로 함께 알린다.
   - **정리 자체는 `plan-feature` 로 넘긴다 — 이 단계가 직접 파일을 옮기거나 지우지 않는다.** 훑어서 알리고 넘기는 데까지가 8번의 일이다.
   - **④ 로 걸린 `SPEC.md` 류는 이 단계가 옮기지도 지우지도 않는다.** 위 4번대로 그 파일도 `@SPEC.md` 줄도 건드리지 않는 것이 정본이다 — 훑기는 **매 세션 읽히고 있다는 사실만 알리고**, 정리는 `plan-feature` 가 그 스킬의 「문서 내용을 다른 파일로 옮길 때」 규칙대로 한다.
   - **「묻지 않고 정리에 들어간다」는 정리를 시작하는 데까지다.** 원본 문서를 지우는 것은 여전히 `plan-feature` 의 이관 규칙을 따른다 — 옮긴 내용이 새 자리에 실제로 들어갔는지 확인한 뒤에만 원본과 연결을 지우고, 일부러 뺀 것은 목록으로 보여 준 뒤 확인받는다.

## 꺼내기 모드 (`/womc eject <이름>`)
인자가 `eject` 로 시작할 때만 이 절차를 수행한다. **womc 플러그인이 주는 정의를 이 프로젝트 안으로 복사해, 사용자가 마음대로 고쳐 쓰게 하는 것**이 목적이다.

꺼낼 수 있는 이름:
- 서브에이전트 — `explore` · `plan` · `implement` · `verify` → `.claude/agents/<이름>.md`
- 스킬 — `plan-feature` · `make-rule` · `harness-audit` → `.claude/skills/<이름>/SKILL.md`

절차:
1. 이름을 안 줬으면 위 목록을 보여주고 무엇을 꺼낼지 한 줄로 묻는다. 목록에 없는 이름이면 목록을 보여주고 멈춘다.
2. 원본을 찾는다 — 설치된 플러그인 폴더의 `agents/`·`skills/` 아래에 같은 이름으로 있다.
   Windows `C:\Users\<사용자>\.claude\plugins\marketplaces\works-on-my-claude\`, mac·linux `~/.claude/plugins/marketplaces/works-on-my-claude/`.
   못 찾으면 GitHub 에서 받는다: `https://raw.githubusercontent.com/yeejh96-bit/works-on-my-claude/main/<원본경로>` (갱신 모드 0-b 와 같은 `curl` 방식).
3. 대상 경로에 파일이 **이미 있으면 덮어쓰지 않고 멈춘 뒤** 알린다 — 사용자가 이미 고쳐 둔 것일 수 있다.
4. 그대로 복사한다. 내용을 요약하거나 손대지 않는다.
5. 무엇을 어디로 꺼냈는지, 앞으로 어떻게 되는지 한국어로 짧게 알린다:
   - **서브에이전트**: 프로젝트 파일이 플러그인 것을 **이긴다**. 이제 이 프로젝트에서는 꺼낸 파일이 쓰이니 마음대로 고치면 된다. 플러그인 기본으로 돌아가려면 꺼낸 파일을 지운다.
   - **스킬**: 다르다. 플러그인 스킬은 항상 `womc:` 이름표를 달고 있어서 **꺼내도 원본이 사라지지 않고 둘 다 살아남는다**(같은 이름 두 개가 보인다). 이 프로젝트에서 꺼낸 쪽만 쓰고 싶으면 부를 때 이름표 없는 쪽을 고르거나, 꺼낸 파일의 이름을 알아보기 쉽게 바꾼다.
6. 꺼낸 뒤에는 Claude Code 를 껐다 켜야 새 정의가 잡힌다고 한 줄 덧붙인다.
