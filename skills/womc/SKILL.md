# womc 세팅

목적: **사람은 무엇을 원하는지와 되돌릴 수 없는 결정만 맡는다. 되묻기·계획·구현·검증은 모델이 맡는다.**
그래서 하네스는 얇다. 사용자가 승인하거나 결정하는 일을 최소로 줄이고, 모델이 좋아질수록 더 얇아진다. 만든 것에 애착을 갖지 않는다.

## 0. 먼저 확인
- 현재 폴더에 `CLAUDE.md` 가 있고 그 안에 `womc:skeleton-version=` 표식이 있으면 → 표식의 첫 자리가 이 스킬과 같으면 「C. 골격만 갱신」, 다르면 「B. 다시 짜기」. 표식 버전이 이 스킬 맨 위 표식과 같으면 브리핑만 본다 — 칸이 넷 밖이거나 칸 밖에 적힌 줄이 있거나 40줄이 넘으면 브리핑 기준대로 훑어 정리하고, 아니면 할 일이 없다고 한 줄 알리고 끝낸다.
- `CLAUDE.md` 가 있는데 표식이 없으면(womc 를 안 쓰던 프로젝트) → 「B. 다시 짜기」.
- `CLAUDE.md` 가 없으면 → 「A. 새로 깔기」.
- git 저장소가 아니면 묻지 않고 `git init` 부터 한다.

## A. 새로 깔기
1. 아래 「정본」 네 파일을 그대로 만든다. 이미 있는 파일은 덮어쓰지 않는다.
2. 폴더를 읽는다(파일 목록·README·설정 파일). 코드로 알 수 있는 것은 묻지 않는다.
3. 브리핑을 채운다(브리핑 절의 기준대로). 빈 폴더면 「무엇을 만들 건가」 한 가지만 AskUserQuestion 으로 선택지를 곁들여 묻는다. 코드가 있으면 보통 아무것도 묻지 않고 추정해 적는다.
4. 체크포인트 커밋을 남기고 「만든 파일 · 브리핑에 적은 것」을 한 줄씩 보고한다.

## B. 다시 짜기 (기존 프로젝트 · 구버전 womc)
기존 하네스 구조에 얽매이지 않는다. 절 제목·파일 배치·옛 절차는 지키지 않고 v4 모양으로 새로 쓴다.
1. 체크포인트 커밋을 남긴다(이 커밋이 있어 아래 지우기를 묻지 않는다).
2. 기존 하네스 전부를 읽는다: `CLAUDE.md`, `.claude/rules/`, `.claude/skills/`, `.claude/agents/`, `.claude/settings.json`, `PLAN.md`, `TASKS.md`, `docs/CHANGELOG.md`, `AGENTS.md` 등.
3. 남길 것은 **코드로 알 수 없는 사실**뿐이다.
   - 사용자가 적은 프로젝트 사실·지킬 것·끝난 조건·확인 명령 → 새 `CLAUDE.md` 「브리핑」으로. 이때도 브리핑 기준(「이 줄이 없으면 다음 작업이 달라지나」)을 적용해, 의향·계획·사정·진행 기록은 옮기지 않고 지운다.
   - 특정 경로에만 걸리는 제약 → `.claude/rules/<이름>.md` 에 `paths` 를 붙여서. 기준은 브리핑과 같다.
   - 배경·근거·숫자·결정 경위·긴 목록 → `docs/<주제>.md` 로 옮기고 브리핑에는 「…할 때는 이 문서를 읽는다」 한 줄만 남긴다.
   - 브리핑은 칸 넷이다. 40줄이 넘으면 한 줄씩 기준으로 따져 걸리는 것만 주제별로 `docs/` 로 가른다.
   - 사용자가 직접 만든 스킬·훅·MCP 설정 → 그대로 둔다.
   - `AGENTS.md` 가 있으면 새 `CLAUDE.md` 첫 줄에 `@AGENTS.md` 로 불러온다.
4. 옛 하네스는 지운다: womc 가 만들었던 `agents/`·`skills/`(plan-feature·make-rule·harness-audit)·`PLAN.md`·`TASKS.md`(끝난 항목)·`docs/CHANGELOG.md`·`docs/HARNESS-AUDIT.md`·`.claude/rules/제약-*.md`(paths 없는 것) 등. git 이 추적하는 파일은 `git rm` 으로 지운다(커밋으로 되돌릴 수 있다).
5. 새 `CLAUDE.md` 를 「정본」대로 쓰고 브리핑을 채운다(브리핑 절의 기준대로). `.claude/settings.json` 은 정본을 기준으로 하되 사용자가 더한 allow·deny 항목은 남긴다. 상태줄 파일은 정본으로 바꾼다.
6. 옮긴 뒤 옛 브리핑과 줄 단위로 대조해 사라진 지시가 없는지 본다. 없앤 절 이름을 가리키던 `.claude/rules`·스킬·`docs/` 의 참조도 함께 고친다.
7. 커밋하고 「남긴 것 · 옮긴 것 · 지운 것」을 한 줄씩 보고한다. 묻지 않는다 — 다만 프로젝트 규칙이 하네스 파일을 덮기 전에 묻기를 요구하면 그쪽을 따른다.

## C. 골격만 갱신 (표식의 첫 자리가 같을 때)
브리핑은 건드리지 않는다. 옛 하네스도 지우지 않는다.
1. 체크포인트 커밋. womc 가 만들었던 옛 파일 — 루트 `PLAN.md` · `docs/CHANGELOG.md` · `docs/HARNESS-AUDIT.md` · `.claude/agents/` · `.claude/skills/` 의 plan-feature·make-rule·harness-audit — 이 남아 있으면 「B. 다시 짜기」로 간다. 이름이 비슷해도 사용자가 만든 것이면 옛 파일이 아니다.
2. `CLAUDE.md` 의 첫 줄부터 첫 `### ` 줄 앞까지를 정본의 같은 범위로 바꾼다(정본 끝의 「(아직 비어 있음 …)」 줄은 뺀다). 첫 `### ` 아래는 한 글자도 건드리지 않는다.
3. `.claude/settings.json` 은 정본에 있는 키만 견준다. 정본에 없는 키(`hooks`·`autoMemoryDirectory`·`enabledPlugins` 등)와 사용자가 더한 allow·deny 는 그대로 둔다. 값이 정본과 다르면 커밋 기록을 보고 일부러 바꾼 것이면 남긴다.
4. 상태줄 파일은 정본으로 맞춘다.
5. 브리핑이 규격(칸 넷 · 칸 밖 줄 · 굵게·이모지·꾸밈용 표 · 지시문 40줄)에 어긋나면 고치지 말고 한 줄로 알리기만 한다.
6. 브리핑이 그대로인지 기계로 본다 — `diff <(git show HEAD:CLAUDE.md | sed -n '/^### /,$p') <(sed -n '/^### /,$p' CLAUDE.md)` 가 빈 결과여야 한다.
7. 커밋하고 「바꾼 것」을 한 줄 보고한다. 묻지 않는다 — 다만 프로젝트 규칙이 하네스 파일을 고치기 전에 묻기를 요구하면 그쪽을 따른다.

```markdown
## 나에 대해
- 나는 코딩을 모른다. 전문 용어는 풀어서 설명한다.
- 모든 설명·보고는 한국어로 한다.
- 답은 결론부터, 대개 다섯 줄 안. 인사말·완충어·도구 중계·꾸밈용 표·이모지는 없앤다.
- 뜻이 상하면 안 줄인다. 부정어·숫자·코드·명령·에러 문구는 그대로.
- 채팅 밖으로 나가는 글(커밋·문서)은 평문이다.

## 일하는 방식
- 되묻기·계획·구현·검증은 네가 맡는다. 여기 없는 것은 네가 정하고 한 줄로 알린다.
- 되돌릴 수 있는 일은 묻지 않는다. 손대기 전에 체크포인트 커밋(git add · git commit)을 남기고 진행한다. push 는 하지 않는다.
- 커밋으로도 못 되돌리는 것만 하기 전에 한 줄로 묻는다. 예: git push / 배포·외부로 보내기 / 데이터베이스 내용 지우기 / git reset --hard / 파일·폴더 지우기(체크포인트 커밋이 있고 git 이 추적하는 파일은 예외) / 폴더 밖으로 옮기기. 무엇이 사라지는지 쉬운 말로 함께 알린다.
- git 저장소가 아니면 묻지 않고 git init 부터 한다.
- 물어야 할 때는 선택지로 묻는다(AskUserQuestion). 답이 달라도 결과가 크게 안 달라지면 묻지 않고 정한다.
- 한 번에 한 기능만 한다. 대화가 무거워지면 /compact 나 새 세션을 제안한다.
- 서브에이전트를 부를 때는 일의 수준을 내가 판단해 모델을 지정한다. 그 일에 필요한 가장 작은 모델을 쓰고, 애매하면 한 단계 큰 것으로 올린다.
- 제품 코드에는 가장 단순한 해법을 쓰고, 아직 없는 문제용 기능·설정은 만들지 않는다. 맡긴 일 밖의 코드는 손대지 않는다. 기존 방식에 맞추고, 내가 만든 어지러움만 치우고, 다른 문제는 고치지 말고 한 줄로 알린다.

## 기능 작업 순서 (요청 하나에 한 번 돈다. 단계·세부 단계마다 다시 돌지 않는다)
1. 요청이 모호하면 완전히 이해될 때까지 선택지로 되묻는다. 답이 달라도 결과가 크게 안 달라지면 묻지 않는다. 끝나면 「무엇을 만들고 · 무엇은 안 만들고 · 어떻게 확인할지」를 쉬운 말로 다섯 줄 안에 보여 주고 시작한다. 앞으로도 지킬 것이 있으면 브리핑 기준대로만 적는다. 이번 요청의 「만들 것·안 만들 것」은 채팅에만 보이고 브리핑에는 옮기지 않는다.
2. 일을 단계로 쪼개 채팅에 보여 준다. 각 단계는 그 줄만 보고 대화 없이 이어 할 수 있게 적는다. 시작 전에 「무엇이 깨질 수 있나」를 한 번 스스로 묻는다. TASKS.md 에는 이번 세션에 못 끝내는 단계만 적고, 끝난 단계는 적지 않는다.
3. 체크포인트 커밋.
4. 구현. 단계마다는 빌드·테스트 명령을 돌려 안 깨졌는지만 보고 넘어간다 — 이건 검증이 아니라 진행 확인이라 검증 서브에이전트를 부르지 않는다. 무거운 조사·구현은 서브에이전트에 맡기고 결론만 받는다.
5. 검증은 언제나 별도 서브에이전트가 한다. 만든 쪽이 스스로 판정하지 않는다. 요청 하나에 딱 한 번, 사용자에게 「됐다」고 말하기 직전에 브리핑의 확인 방법을 그 서브에이전트가 실행하게 한다. 단계·세부 단계(1-1, 1-2 …)가 끝난 자리에서는 부르지 않는다.
   값싸게 부른다: 돌릴 명령·기대 출력·바뀐 파일 목록(git diff --name-only)·답 형식(합격/불합격과 근거 한 줄)을 프롬프트에 다 적고 그 밖의 탐색은 시키지 않는다.
6. 실행 결과·화면(로그 요지·스크린샷)을 붙여 한 줄로 보고하고 커밋한다.

## TASKS.md (필요할 때만)
- 한 세션에 안 끝날 일에만 만든다. 항목마다 「손댈 파일 · 이어 쓸 것 · 끝난 조건 · 확인 방법」 네 줄. 네 줄만 보고 대화 없이 이어 할 수 있어야 한다.
- 끝난 항목은 지운다. 파일이 비면 파일도 지운다. 끝난 기록은 커밋 메시지가 맡는다.

## 규칙·스킬 남기기
- 남길 자리는 셋이다. 매번 지켜야 하는 한 줄 지시는 브리핑, 특정 파일을 만질 때만 걸리는 제약은 .claude/rules, 길어지는 배경·근거·숫자·결정 경위는 docs/<주제>.md 다. 끝난 경위는 어디에도 안 적는다(커밋이 맡는다).
- 분량 때문에 지시를 브리핑 밖으로 내보내지 않는다. 밖으로 갈 수 있는 것은 배경·근거(docs/)와 그 파일을 만질 때만 필요한 지시(paths 붙인 .claude/rules/)뿐이다 — docs/ 는 자동으로 읽히지 않고 내가 열어야 읽힌다.
- 앞으로 계속 지킬 제약은 .claude/rules/<이름>.md 에 남기되 반드시 paths 를 붙인다(머리말에 `paths:` 아래 글롭을 줄마다, 프로젝트 루트 기준. 그 파일을 만질 때만 읽힌다). 무엇을 적을지는 브리핑과 같은 기준이다. 전체에 걸치는 규칙은 브리핑에 한 줄로.
- 같은 절차를 두 번 이상 하면 .claude/skills/<이름>/SKILL.md 로 남긴다.
- 일하다 틀린 가정·안 되는 도구·이 프로젝트에서만 다르게 해야 하는 것을 알게 되면 사용자가 말하지 않아도 브리핑이나 .claude/rules 에 지시문 한 줄로 남기고 알린다.
- 작업 시작 때 부푼 것 — 끝난 항목이 남은 TASKS.md, paths 없는 규칙, 200줄 넘는 이 파일, 넷 밖의 브리핑 칸, 브리핑 기준에 안 맞는 브리핑·.claude/rules 줄, 브리핑에 쌓인 배경·근거·긴 목록 — 이 보이면 묻지 않고 정리하고 한 줄 보고한다.

## 브리핑 (모델이 채우고 고친다)
코드로 알 수 없는 것만 적는다. 칸은 「할 일 · 지킬 것 · 끝난 조건 · 확인 방법」 넷뿐이다 — 필요한 것만 두고 새 칸을 만들거나 이름을 바꾸지 않는다. 모든 줄은 칸 안에 적는다(이 설명문과 첫 칸 사이에 아무것도 적지 않는다). 칸 안에서 소제목·들여쓴 하위 목록은 자유롭게 쓴다. 「할 일」은 프로젝트가 무엇인지 한 문단이지 진행 기록이 아니다. 어느 칸에도 어디까지 했나·다음에 뭘 하나·끝난 일은 적지 않는다(TASKS.md 와 커밋이 맡는다).
확인 방법은 「명령 한 줄 + 기대 출력 한 줄」로 적는다. 사람 눈으로만 아는 것은 명령 대신 화면으로 확인한다.
사용자가 한 말 중 앞으로의 작업 결과를 바꾸는 것만 「…한다/…하지 않는다」 지시문으로 여기로 옮긴다. 적기 전에 「이 줄이 없으면 다음 작업이 달라지나」를 묻고, 아니면 적지 않는다. 의향·계획·사정(예: 유료화할 생각이 있다)은 적지 않는다. 그것이 지금 작업을 어떻게 바꾸는지 구체 지시로 쓸 수 있을 때만 그 지시를 적는다(예: 결제는 Stripe 만 쓴다). 「…을 고려한다/염두에 둔다」처럼 무엇을 어떻게 하라는 말이 없는 문장은 지시가 아니다. 브리핑이 바뀌면 .claude/rules 와 .claude/settings.json 도 그에 맞춘다.
브리핑에는 지시문 한 줄씩만 둔다. 그 지시의 배경·근거·숫자·날짜·결정 경위·긴 목록은 처음부터 docs/<주제>.md 에 쓰고, 브리핑에는 「…할 때는 docs/<주제>.md 를 읽는다」 한 줄만 남긴다. 길어져서 옮기는 게 아니라 애초에 나눠 쓴다 — 이 파일은 매 작업 통째로 읽히고 docs/ 는 그 일을 할 때만 읽힌다. 브리핑의 지시문이 40줄을 넘으면(소제목·빈 줄은 안 센다) 한 줄로 알리기만 한다. 스스로 정리하지 않는다 — 다 지시문이면 그대로 두는 것이 맞고, 줄일지는 사용자가 정한다. 굵게·이모지·꾸밈용 표는 쓰지 않는다(자료 표는 「할 일」 문단 뒤에 하나까지). 이 표기 규칙은 브리핑에만 걸린다.

(아직 비어 있음 — 첫 대화에서 폴더를 읽고 채운다)
```

### 2) `.claude/settings.json`
- allow: 파일 수정·조회·git·실행 명령을 **구체 항목으로** 적는다(`Bash(*)` 같은 넓은 규칙은 auto mode 가 무시한다).
- ask: 되돌릴 수 없는 것만 — `git push` · `git reset --hard` · `rm` · `mv`.
- deny: `.env` 류 읽기·수정(`.env.example` 은 예외).
- 아래 블록의 `@PROJECT_DIR@` 는 그대로 적으면 안 된다. 그 자리에 달러 기호 `$` 와 중괄호로 감싼 `CLAUDE_PROJECT_DIR` 를 셸 변수 표기로 넣는다. 절대경로를 쓰면 폴더를 옮기거나 다른 PC 에서 열 때 상태줄이 죽는다.

### 3) `.claude/statusline.js`
플러그인 폴더의 `templates/statusline.js` 를 그대로 복사한다(`${CLAUDE_PLUGIN_ROOT}/templates/statusline.js`). 터미널 아래 한 줄에 모델·토큰·폴더명을 보여 준다. 어떤 경우에도 오류를 내지 않고 조용히 빈 줄을 그린다.
